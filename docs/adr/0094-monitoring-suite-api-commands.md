# ADR 0094: Monitoring Suite API コマンドを追加する

- Status: Accepted
- Date: 2026-11-19
- SDK: `github.com/sacloud/sacloud-sdk-go v0.7.0` (`api/monitoring-suite`)

## Context

モニタリングスイートは、ログ・メトリクス・トレースの保存領域 (ストレージ) と、それらを他サービスから送信するためのルーティング、メトリクスに基づくアラート (アラートプロジェクト、ルール、通知先、通知ルーティング、ログ計測ルール)、ダッシュボードプロジェクト、契約管理 (リソース上限、プロビジョニング状態) を提供する ([モニタリングスイートのマニュアル](https://manual.sakura.ad.jp/cloud/appliance/monitoring-suite/index.html))。

SDK (`api/monitoring-suite`) は 13 リソース・94 操作を公開し、うちラッパー層が 90 操作を公開する。API は Ogen 系の独立したドメインで、IaaS API ([ADR 0081](0081-high-level-command-users-manual.md) の前提となる IaaS コマンド群) ではなく、`<domain>api` コマンドとして配置する ([ADR 0074](0074-api-command-name-structure.md))。sakumock v0.14.0 にモックサーバーがある。

操作の入力には次の形がある。

- ストレージの作成 (名前、説明、区分、KMS キー、サービスプリンシパル) やアラートルールの作成 (名前、クエリ、しきい値) のように、独立した単純スカラー値で有効なリクエストを表現できる操作。
- 通知ルーティングの作成 (ラベルマッチャーの配列) や並べ替え (UID と順序の配列)、プロビジョニング初期化 (ログ・メトリクス領域ごとの有無)、ログ計測ルール (version 付きの構造化クエリ) のように、配列やネストした構造を要求する操作。
- アラートルールの `query` は PromQL 形式の文字列で、取得操作の jq 式 (`--query` は CLI の共通オプション) と名前が衝突する。

## Decision

- `monitoring-suite-api` を追加する。SDK がラッパー層で公開する 90 操作のうち 88 操作を生成器で生成し、2 操作を手書きする。手書きは (1) `list-alert-project-histories` (SDK パラメータ型の配列フィールドを severity と open の個別フラグへ展開)、(2) `create-alert-project-notification-target` (URL を `url.URL` として解析して形式を検証) とする。生成コマンドの命名は `<動詞>-<対象>` のフラット構造とし、部分更新は `patch-*` とする。
- 独立した単純スカラー値で有効なリクエストになる操作は個別フラグを設ける。配列・ネスト構造を要求する操作 (通知ルーティングの作成と並べ替え、プロビジョニング初期化、ログ計測ルールの作成と部分更新) は `--request` JSON 経路のみとし、個別フラグは設けない。JSON キーは SDK パラメータ型のフィールド名、ogen 型由来の部分は API の JSON 名 (snake_case) に従う。
- アラートルールの `query` に対応するフラグは `--alert-query` とする。CLI の共通オプション `--query` (jq 式) との衝突を避けるためで、ヘルプに PromQL 形式であることを記載する。
- ストレージの保存期間変更 (`set-log-storage-expire`、`set-trace-storage-expire`) は、SDK が日数を位置引数として受け取るため `--days` フラグにする。ストレージのアクセスキー操作は `<storage>-key` を対象にした個別コマンドとし、キーの UID は位置引数で受け取る。
- ライブ検証で確認した実 API の入力規則をヘルプに反映する。(1) ダッシュボードプロジェクト作成の `description` は必須 (省略したリクエストは 500 になる)。(2) アラートルールの `threshold_warning` / `threshold_critical` は比較演算子を先頭に付けた形式 (例: `>=70`)。(3) `enabled_warning` と `enabled_critical` は少なくとも一方を true にする必要がある。(4) `query` は PromQL 形式。詳細は設計文書に記録する。
- ライブ E2E は `test/e2e/monitoring-suite/` に testing.T ベースのシナリオとして配置する ([ADR 0062](0062-e2e-testing-t-based-scenario.md))。読み取り系コマンドに加え、ダッシュボードプロジェクト、アラートプロジェクト、メトリクス・ログ・トレースの各ストレージ、アクセスキー、アラートルール、通知先、通知ルーティング (並べ替えを含む)、ログ計測ルール、ログ・メトリクスルーティング、履歴の一覧を検証する。作成した課金リソースはすべてテスト内で削除し、削除後の不在を確認する。既存のリソースとプロビジョニング状態 (`initialize-provisioning`) は変更しない。
- `initialize-provisioning` は CLI 操作テスト (sakumock) で検証するが、ライブ E2E では実行しない。既存環境のプロビジョニング状態を変更する操作であり、テスト専用アカウントでも既存の保存領域の構成に影響するため、対象外とする。

## Consequences

- モニタリングスイートの主要な作業 (ストレージ作成、アラート設定、ルーティング、履歴確認) を CLI で完結できる。複雑な構造は JSON 経路で送れる。
- アラートルールの `--alert-query` は他のリソースと異なるフラグ名になる。ヘルプとチュートリアルで案内する。
- sakumock は実 API より入力検証が緩いため、CLI 操作テストでは実 API の入力規則の一部を検証できない。実 API の規則はライブ E2E とヘルプで補う。差分は sakumock の差分管理文書に記録する。
- ライブ E2E はメトリクス・ログ・トレースの各ストレージを作成するため、実行ごとにストレージの課金が発生する (作成して削除する)。実行は明示的な `SKR_E2E=1` のときに限られる。

## Alternatives considered

- 通知ルーティングのマッチャー配列を反復可能な key=value オプションにする案: 要素のフィールド (名前、値、種別) が PromQL のラベルマッチャーに対応する構造であり、意味を明確に表せるが、対象が 1 操作に限られ、[ADR 0041](0041-server-repeatable-disk-and-nic-options.md) の適用範囲を拡張する合意が必要になる。今回は `--request` JSON にとどめ、必要になった時点で検討する。
- `--alert-query` の代わりに `--rule-query` など他の名前にする案: 対象フィールドが API の `query` であることを名前で示すため `--alert-query` を採用した。ほかのリソースで `query` フィールドが現れた場合は、同じ原則 (`<対象>-query`) で衝突を回避する。
- プロビジョニング初期化をライブ E2E に含める案: 既存環境の保存領域構成を変更するため採用しない。CLI 操作テストとヘルプで検証する。
