# ADR 0083: AppRun Dedicated 高レベルコマンドにインフラライフサイクルスケルトンを追加する

- Status: Accepted
- Date: 2026-11-13

## 背景

[ADR 0079](0079-apprun-dedicated-high-level-commands.md) では、`skr apprun-dedicated` の高レベル層をアプリケーションデプロイフローに限定し、クラスタ、オートスケーリンググループ、ワーカノード、ロードバランサ、証明書、サービスクラスの参照・管理は低レベル `apprun-dedicated-api` が担うことにしました。

[#257](https://github.com/sacloud/skr/issues/257) では、チュートリアルでオートスケーリンググループの作成後の healthy 待ち、グループやクラスタの削除後の不在確認が多すぎる問題が指摘されています。これらの待ち合わせは API 呼び出しの組み合わせであり、利用者が自前のシェルループで実装するのは高レベルコマンドの思想と不整合です。一方で、クラスタ作成を除くライフサイクルの骨格を高レベル層に持つことで、チュートリアルと利用者スクリプトを簡潔にできます。

高レベル層で待ち合わせを吸収する方針は [ADR 0082](0082-high-level-command-wait-options.md) で決定しました。

## 決定

- [#257](https://github.com/sacloud/skr/issues/257) の案 A を採用します。`skr apprun-dedicated` に以下の高レベルコマンドを追加します。
  - `create-auto-scaling-group`: クラスタ名、グループ名、ゾーン、ワーカサービスクラス、ノード数を指定してオートスケーリンググループを作成し、ワーカノードが healthy になるまで待ちます。
  - `delete-auto-scaling-group`: クラスタ名とグループ名でグループを特定して削除します。`--no-wait` 指定時も削除 API の呼び出しと削除後の不在確認は行い、削除 API 呼び出しから実際に削除されるまでの待機のみを省略します。
  - `delete-cluster`: 関連リソース（アプリケーション、オートスケーリンググループなど）が残っていれば列挙して中断し、なければクラスタを削除します。`--no-wait` 指定時も依存確認、削除 API の呼び出し、削除後の不在確認は行い、削除 API 呼び出しから実際に削除されるまでの待機のみを省略します。
- これらのコマンドは [ADR 0082](0082-high-level-command-wait-options.md) に従い、negatable な `--wait` (自動生成される `--no-wait` で待機を省略) と `--wait-timeout` を持ちます。
- 削除系コマンドは確認プロンプトを持ち、`--force` で省略します。
- クラスタ作成は設定が複雑なため、高レベル層の対象外とします。低レベル `apprun-dedicated-api create-cluster` (`--request` JSON) を使ってください。
- ロードバランサ、証明書、ワーカノードの draining、サービスクラスは対象外とします。

## 影響

- チュートリアルからオートスケーリンググループ作成・削除の待ちループと ID 抽出が消え、クラスタ削除前の依存確認もコマンドに組み込まれます。
- `skr apprun-dedicated` の対象と対象外を言い直す必要があります。「アプリケーションデプロイフロー」のみではなく、「デプロイフローとインフラのライフサイクル骨格」となります。
- 追加コマンドの実装時には、service 層 (`service/apprun-dedicated-service-go`)、CLI 層 (`internal/apprundedicated`)、ライブ E2E、チュートリアル、ユーザーズマニュアルの更新が必要です。
- ライブ E2E はクラスタ作成を前提とするため、実行コストと承認は [#59](https://github.com/sacloud/skr/issues/59) で管理します。

## 検討した選択肢

- 案 B の汎用 `wait` サブコマンド: スコープ増は小さい一方、高レベルコマンドの「作業単位を内製する」思想から外れ、ID 配管が残るため採用しません。
- クラスタ作成も高レベルに含める方式: 設定が複雑で `--request` JSON が必要になり、高レベル層で簡潔に表現できる部分が少ないため採用しません。
- インフラライフサイクルを低レベルのままにし、チュートリアルの待ちループを残す方式: 高レベルコマンドの価値が損なわれ、利用者が API のエラー文言に依存しやすくなるため採用しません。
