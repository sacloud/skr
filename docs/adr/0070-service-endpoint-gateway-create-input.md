# ADR 0070: Service Endpoint Gateway Create の入力経路

- ステータス: 承認済み
- 日付: 2026-10-30

## 背景

サービスエンドポイントゲートウェイ (`service-endpoint-gateway-api`) を追加するにあたり、Create の入力経路を決める必要がある。API の作成リクエストは、クラス名とプラン ID が固定値であり、利用者が指定する項目は接続先スイッチ ID、IPv4 サブネットのネットマスク長、ゲートウェイ配下のサーバー IP アドレスの配列 (備考情報の `Remark`) のみである。

[ADR 0007](0007-api-request-input.md) と [ADR 0035](0035-iaas-tags-flag.md) では、`--request` と個別フラグを相互排他で設け、複雑な値や配列は JSON 入力に残す方針である。[ADR 0041](0041-server-repeatable-disk-and-nic-options.md) の Server Create の `--disk` / `--nic` は、複数ディスクの所属を表現するための例外であり、他の配列へ自動適用しない。

サービスエンドポイントゲートウェイの作成リクエストは、独立した単純なスカラー値 (スイッチ ID、ネットマスク長) と、サーバー IP のみからなる単純な文字列の配列で有効なリクエストを表現できる。ADR 0007 の「独立した単純なスカラー値で有効なリクエストを表現できる場合に限りフラグ化する」方針に沿うかどうかを判断する。

## 決定

Create に個別フラグと `--request` の両経路を設け、相互排他とする。

- 個別フラグは必須の `--switch-id`、`--network-mask-len` と、任意で繰り返し指定できる `--server-ip` とする。`--server-ip` はサーバー IP アドレスを 1 要素として受け付け、指定順に API リクエストの `Servers` 配列を組み立てる。未指定の場合は空配列を送る。
- クラス名 (`serviceendpointgateway`) とプラン ID (`1`) は、API リクエストの構築時に CLI と SDK が固定値を設定するため、利用者の入力経路には設けない。
- `--request` は、利用者が指定する備考情報のみを受け付ける。`Class` と `Plan` は自動設定されるため JSON に含める必要がないことをヘルプに明記する。API リクエスト全体の JSON を要求すると、利用者が制御できない固定値の記述を強制することになるため、受け付け範囲を `Appliance.Remark` に限定する。Remark のデコードは、スイッチ ID、ネットマスク長、サーバー配列の指定を検証する。
- `--request` と個別フラグは相互排他とし、暗黙にマージしない。[ADR 0041](0041-server-repeatable-disk-and-nic-options.md) の Server Create と同じ方針であり、新しい `key=value` 構文は導入しない。サーバー IP は単純な文字列のため、`--server-ip` の繰り返しで表現できる。
- サーバー IP アドレスの形式、サブネットへの所属、スイッチの種類 (スイッチ単体とルータ＋スイッチの区別) は CLI で検証せず、API の応答に委ねる。
- Update の `Settings` は、有効化するサービスごとに構造が異なるため、`--request` JSON のみを受け付ける。Settings は全体置換であることをヘルプに明記する。

## 影響

- 作成に必要な項目を 1 行で表現でき、チュートリアルとライブ E2E を `--request` JSON なしで書ける。サーバー IP の配列も `--server-ip` の繰り返しで表現できる。
- 手書きの入力処理と検証が必要になる。正常系 (フラグ経路、JSON 経路、ファイル経路) とエラー系 (相互排他、必須フラグの欠落、JSON の解析エラー) は、ドメインパッケージの単体テストで検証する。
- `--request` の受け付け範囲を API リクエスト全体から `Appliance.Remark` に限定するため、ヘルプに受け付ける JSON の構造を明記する。範囲を限定するのは今回の Create だけの判断であり、他の操作の `--request` には適用しない。
- `--server-ip` の繰り返しは、Server Create の `--disk` / `--nic` のような `key=value` 構文ではない。単純な文字列の配列であるため構文解析を追加せず、他の配列への自動適用もしない。

## 検討した選択肢

- **`--request` のみにする案**: 作成の主要な作業が 1 行で完結せず、チュートリアルと E2E が読みにくくなる。リクエストが単純なスカラー値で表現できるため、個別フラグを設けない根拠がない。採用しない。
- **`--request` に API リクエスト全体の JSON を要求する案**: クラス名とプラン ID は利用者が制御できない固定値であり、記述を強制すると入力が冗長になる。採用しない。
- **`--server-ip` を `key=value` 構造化オプションにする案**: 指定する値が IP アドレス 1 個のみであり、キーを導入する意味がない。採用しない。
- **Update の Settings も個別フラグ化する案**: 有効化するサービスごとにエンドポイント一覧や DNS 転送の設定など異なる構造を持ち、フラグ化すると対象範囲が広がりすぎる。JSON 入力に残す。
