# ADR 0005: 低レベル API と高レベルコマンドを分ける

- Status: Proposed
- Date: 2026-10-05

## Context

sacloud-sdk-go は、API 操作用のパッケージと、service layer を提供しています。SDK の操作を直接 CLI から利用する経路と、複数の操作をユーザーの作業単位にまとめる経路の両方が必要です。

EventBus には process-configuration、schedule、trigger の API 操作があり、設定の関連付けや secret 登録を含む利用手順があります。IaaS には多数の API と service package があり、リソースごとに公開操作や前提条件が異なります。

## Decision

- `<domain>-api` を低レベルコマンドの名前空間とし、SDK の公開操作メソッドを CLI 操作に 1 対 1 で対応させます。生成対象は SDK の採用バージョンごとに確認し、SDK にない操作を暗黙に追加しません。
- `<domain>` を高レベルコマンドの名前空間とし、skr 内の service layer を実装して CLI から利用します。この層は SDK の API 操作を組み合わせてユーザーの作業単位を提供します。
- 初期に設計する名前空間は `iaas-api` / `iaas` と `eventbus-api` / `event` です。SDK に存在する全 API グループを一括して実装するものではありません。
- IaaS API が現状 OpenAPI 定義ではないことは SDK の定義形式の違いであり、service layer であることを意味しません。低レベル `iaas-api` は SDK の公開操作を基準に設計します。SDK 内のパッケージ配置から skr の高レベル層を決めません。
- 高レベルコマンドの定義形式や個別ライフサイクルは、対象サービスの SDK と公式ドキュメントを調査したうえで別途決定します。secret は定義、差分、ログ、出力に含めません。
- 詳細設計と SDK `v0.3.0` 時点のリソース調査は [CLI コマンド体系の設計](../design/cli-command-architecture.md)に記録します。

## Consequences

- SDK の操作を個別に実行する入口を広く提供でき、API に対する薄い操作とユーザー向けワークフローの責務が分離されます。
- 低レベルコマンドは SDK の更新に追従し、生成物、ヘルプ、テストの再確認が必要です。
- 高レベルコマンドでは、定義と実リソースの対応、操作順序、差分、削除範囲、secret の扱いを明確に設計する必要があります。
- SDK に service layer がないドメインでは、同じ高レベル機能が自動的に得られるわけではなく、必要なワークフローを skr 側で実装・検証します。

## Alternatives considered

- 高レベルコマンドだけを提供する方法: SDK の個別操作を直接使いたい利用者の経路がなくなるため採用しません。
- SDK 操作をすべて単一の汎用コマンドに集約する方法: 操作固有の型、引数、ヘルプを明示しにくいため採用しません。
- 高レベルコマンドから低レベル CLI を子プロセスとして実行する方法: SDK の型やエラーを直接扱えず、テストと入出力の制御が複雑になるため採用しません。
