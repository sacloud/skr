# ADR 0043: PacketFilter ルール配列の JSON 入力

- Status: Accepted
- Date: 2026-10-15

## Context

PacketFilter の `Expression` はプロトコル、ネットワーク、ポート、アクションなど複数の値を持つルールの配列です。各要素を独立したフラグにすると入力とヘルプが複雑になり、複数ルールの順序を表すための追加設計も必要になります。一方、完全な `--request` JSON だけでは、名前などの単純な値を設定するときにもリクエスト全体を組み立てる必要があります。

## Decision

- `Zone`、`Name`、`Description`、ID などの単純な値は個別フラグで受け付けます。
- ルール配列は JSON 入力とし、作成・更新時に `--expressions` で JSON 配列を直接、または `@path.json` から受け付けます。
- `--expressions` は JSON 値を受け取る入力であり、ルール要素の各フィールドを個別フラグにはしません。1回のコマンドで指定できる JSON 配列は1つです。
- `--request` は従来どおり完全なリクエスト JSON を受け付けます。`--request` と個別フラグ、`--expressions` は併用できません。
- ルール更新時は、読み取り結果の `ExpressionHash` を `OriginalExpressionHash` に指定することを SDK 呼び出し前に検証します。フラグと JSON の両方で指定できます。
- ライブ E2E はフィルタの管理操作とルール内容を検証し、NIC への適用や実際の通信には影響を与えません。

## Consequences

- 少数の基本値はコマンドラインで指定でき、ルール配列もインライン JSON またはファイルで準備できます。
- ルールのフィールド名や形式は JSON で確認する必要があります。複雑なルールを多数指定する場合はファイル入力が適しています。
- ライブ E2E はリソース管理とルール設定の確認に限定され、NIC に適用したときの通信動作を確認するものではありません。

## Alternatives considered

- ルールの各フィールドを個別フラグにする方法: ルールが増えるほど同種のフラグを繰り返す構文が複雑になるため採用しません。
- 完全な `--request` JSON のみを使う方法: 単純な名前やゾーンまで JSON オブジェクト内へ記述する必要があり、基本操作の入力が煩雑になるため採用しません。
