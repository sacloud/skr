# ADR 0058: 全サブコマンドをライブ E2E の検証対象にする

- Status: Accepted
- Date: 2026-10-23

## Context

Object Storage の初期ライブ E2E はバケットの作成・一覧・削除だけを対象にしており、チュートリアルのパーミッションやアクセスキー操作を網羅していませんでした。チュートリアルにないサブコマンドもあり、代表的な操作だけの成功ではサービス全体の検証状況が分かりませんでした。

## Decision

- チュートリアルへの掲載有無にかかわらず、公開するすべての末端サブコマンドには、少なくとも1回正常実行するライブ E2E テストを必須とします。
- サービスごとに複数のシナリオや runner を用意できます。アカウント作成や依存サービスを必要とする操作は、前提条件と副作用を明示した独立シナリオに分けます。
- コマンドとシナリオの対応を検査し、シナリオ実装済み、ライブ成功済み、API エラー、依存不足や合意による延期を区別して設計文書と `PLAN.md` に記録します。
- fake の正常応答、`--help`、エラー応答、空出力だけではライブ成功済みとしません。応答内容と期待値を照合し、変更操作は設定反映と後片付けも検証します。
- Object Storage は6シナリオで34末端コマンドを対象にします。暗号化のライブ実行は、KMS キー作成が未実装のため、利用者との合意により [#141](https://github.com/sacloud/skr/issues/141) に切り出します。
- 認証、実環境変更の承認、確認フラグ、所有確認、秘密情報の保護、失敗時の後片付けは従来の要件を維持します。

### 配置と命名

- サービス・リソースごとの `test/e2e/<service-or-resource>/` と、その配下の独立シナリオ用ディレクトリは kebab-case にします。
- runner の入口は `main.go` とし、同じ runner のシナリオ別実装は `scenario_<snake_case>.go` にします。対応する単体テストは同名の `_test.go` とし、横断テストは `scenarios_test.go` に置けます。
- 共有処理は `input.go` や `cleanup.go` のように役割を表す名前にします。曖昧な `advanced.go` や連番だけのファイル名は使いません。
- 証跡のサービス識別名は `<service-or-resource>-<scenario>`、ステップ名は kebab-case にします。連番・日時・衝突回避は共通の evidence 機構に任せ、秘密情報を名前に含めません。`config` は `c0nfig` に置き換えます。
- 新規作成・分割時に適用し、既存 runner は一括改名しません。改名する場合は実行コマンドと文書の参照も更新します。

## Consequences

- チュートリアルにない更新・削除・補助操作の検証漏れも検出できます。
- 前提条件の異なる操作を無理に1回の実行へまとめず、独立して再実行できます。
- 全コマンドを runner に実装しても、実サービスで正常応答を確認できなければ、検証完了とは報告できません。
- 依存サービスが未実装の場合や実 API が失敗する場合は、追跡 Issue と残作業を明示します。既存サービスの網羅性も、各サービスの作業時に確認します。
- `AGENTS.md` と3つの API 開発スキルで、共通の命名規則と検証範囲を参照できます。通常の `go test` で実環境変更を起こさず、runner の明示実行と単体テストを区別できます。

## Alternatives considered

- チュートリアル掲載手順だけを検証する案は採用しません。チュートリアルの構成によって公開操作の検証漏れが発生するためです。
- 1サービスを必ず1シナリオにまとめる案は採用しません。必要な権限やサイト、依存リソースが異なり、再実行と安全な後片付けが難しくなるためです。
- 未実行や API エラーを成功扱いでスキップする案は採用しません。正常動作を確認できた範囲が分からなくなるためです。
