# ADR 0016: 低レベル API コマンドの定型コードを生成する

- Status: Accepted
- Date: 2026-10-05

## Context

`<domain>-api` のコマンドは、SDK の公開操作を CLI から実行する低レベルの入口です。リソースごとにコマンド登録、入力の解析、SDK 操作の呼び出し、出力処理を実装するため、同じ形のコードを繰り返し手書きすると実装やテストの一貫性を保ちにくくなります。

たとえば `switch.go`、`simplemq.go`、`eventbus.go` には、それぞれ定型的な操作処理と、ゾーン横断検索、プロバイダークラスの設定、秘密情報の安全な読み込みなどの固有処理が混在しています。後者は SDK の型情報だけから正しく導けるものではありません。

[awslim](https://github.com/fujiwara/awslim) は対象サービスやメソッドを設定し、AWS SDK の型情報とテンプレートから Go コードを生成しています（[生成器](https://github.com/fujiwara/awslim/blob/main/cmd/awslim-gen/main.go)、[設定からの生成](https://github.com/fujiwara/awslim/blob/main/cmd/awslim-gen-gen/main.go)）。一方、sacloud-sdk-go には IaaS のサービス操作や OpenAPI 由来の API など異なる形式があり、サービス固有の入力条件や CLI 上の説明も必要です。SDK のメソッドを一律にコマンドへ変換する方法は適しません。

## Decision

- 低レベル API コマンドでは、繰り返し発生するコマンド登録、SDK 操作への接続、標準的なリクエスト受け渡しと出力処理を、明示的な設定に基づいて Go コード生成できるようにします。
- 生成対象のサービスと操作は明示的に選びます。SDK の公開メソッドを検出しただけで、すべてを CLI に追加することはしません。
- SDK の公開シグネチャと型を操作・リクエストの技術的な根拠にし、CLI 上の操作名、フラグの対応、必須入力、ヘルプ文、サービス固有の処理は設定または手書きの実装で明示します。生成器はこれらの意味を SDK の型だけから推測しません。
- リクエストのフラグ化は [ADR 0007](0007-api-request-input.md) に従います。フラグ経路と `--request` の相互排他、未指定値の保持、複雑な値や `null` の扱いを生成後も維持します。
- ゾーン横断検索、プロバイダークラスの自動設定、秘密情報、リソース固有の入力変換など、標準化できない処理は手書きの実装として残します。生成部分と手書き部分の境界は、生成器が個別サービスの動作を隠さない形にします。
- 生成した Go ファイルはリポジトリに含め、生成物に手を加えず再生成できるようにします。生成器のテストに加え、対象コマンドの SDK 呼び出し、入力、出力、エラー経路を既存のモックやテストで検証します。
- 導入は対象を絞って段階的に行います。既存コマンドの一括移行や、高レベルコマンドの生成はこの決定に含めません。

## Consequences

- 定型コードの書き方が揃い、同種の低レベル API コマンドを追加するときの手作業とレビュー差分を減らせます。
- SDK の公開シグネチャと生成対象の対応を再確認しやすくなります。SDK 更新時は生成器を再実行し、生成差分と対象コマンドの動作を検証します。
- 生成器、設定、テンプレートを保守する負担が加わります。対象操作の選定やヘルプ、入力規則には引き続き人による判断が必要です。
- SDK の API 定義形式や操作ごとの差異があるため、すべてのコマンドを一種類のテンプレートで生成できるとは限りません。例外を無理に共通化せず、生成対象外として手書きにできます。
- 生成物をリポジトリに含めるため、通常のビルド時に生成器へ依存しません。一方、生成前後の差分を確認する手順と、生成済みコードを直接編集しない規則が必要です。

## Alternatives considered

- AI がコマンドを毎回手書きする方法: 小さく始められますが、同種の処理を繰り返し実装するため一貫性を保ちにくく、SDK 更新時の追従も個別作業になります。
- SDK の全公開操作を自動的に CLI に公開する方法: コマンド範囲や利用者向けの説明、必須入力、サービス固有の挙動を SDK の型だけでは決められず、意図しないコマンド公開につながるため採用しません。
- すべての処理を汎用ランタイムで動的に実行する方法: 操作ごとの型安全性やヘルプ、エラー処理を明示しにくく、既存の Kong コマンド構成とも合わないため採用しません。
- 定型処理も含め、すべて手書きのままにする方法: 個別の例外を自然に扱えますが、繰り返し部分の一貫性を改善できないため採用しません。
