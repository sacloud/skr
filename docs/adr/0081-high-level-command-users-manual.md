# ADR 0081: 高レベルコマンドのユーザーズマニュアル

- Status: Accepted
- Date: 2026-11-12

## Context

高レベルコマンドは低レベル API コマンドの 1 対 1 の合成ではなく、独自の意味論を持つ (例: `skr apprun-dedicated` の deploy は「クラスタとアプリケーションの検索、バージョン作成、有効化、反映待ち」を 1 つのコマンドにまとめ、`registryPasswordAction` を文脈から決定する)。この挙動の説明は design doc (開発者向け、利用者向けサイトには公開しない) にしかなく、利用者向け資料は手順を示すチュートリアルのみだった。

チュートリアルは代表的な作業の順序を示すもので、すべてのサブコマンドとフラグの挙動、制約、エラーの意味を網羅しない。一方、コマンドリファレンスの役割は既に `--help` (docs サイトの `commands/index.html` で自動公開) が担っているため、手書きのリファレンスを追加するとヘルプとの記載が二重化し、乖離するリスクが生じる。

## Decision

高レベルコマンドには、チュートリアルに加えてユーザーズマニュアル (コマンドリファレンス) を `docs/manual/<service>.md` として作成する。

- 最初の対象は `docs/manual/apprun-dedicated.md`。EventBus など他の高レベルコマンドは追跡 Issue で順次作成する。
- 役割分担を次のようにする。マニュアルは対象と対象外、概念モデル、コマンドの構造と低レベル API との対応、各サブコマンドの挙動と制約、定義ファイルや入力の形式、エラーと対処を説明する。フラグと使用例の網羅的な一覧はヘルプに任せ、マニュアルでは繰り返さない。手順はチュートリアルに任せ、相互にリンクする。
- マニュアルに記載する挙動は、実装したヘルプと design doc の記載と照合する。サービス側の上限値やレート制限の数値は記載せず、公式マニュアルへの参照で示す。
- **高レベルコマンドを新規に追加する場合、および既存の高レベルコマンドの挙動や入力を変更する場合は、対応するマニュアルを作成・更新する。** このルールを AGENTS.md に記載し、作業時に漏れないようにする。

## Consequences

- 利用者は手順を読まずに、コマンドの構造、挙動の意味論、制約、エラーの意味を確認できる。
- ヘルプとマニュアルで同じ内容を書く範囲が明確になり、記載の乖離を小さく保てる。ヘルプの文言変更時はマニュアルの該当箇所も見直す。
- 高レベルコマンドを追加するたびにマニュアルの作成が必須になり、ドキュメント作業が増える。EventBus の分は [issue #251](https://github.com/sacloud/skr/issues/251) で追跡する。
- design doc とマニュアルで同じ挙動を異なる読者向けに説明することになる。design doc の記載が変更された場合もマニュアルの該当箇所を見直す。

## Alternatives considered

- チュートリアルにリファレンス的な節を追加する: 1 ファイルで完結するが、手順と解説が混在して肥大化し、特定の手順を読んでいない利用者が参照しにくい。既存の apprun-dedicated のチュートリアルは 471 行あり、さらに追加する規模ではない。
- 手書きのリファレンスを作らずヘルプの自動公開だけで足りるとする: `--help` の出力はコマンド単位で断片的であり、低レベル API との対応や定義ファイルの意味論など、コマンド群を横断して初めて分かる内容を説明できない。高レベルコマンドの独自の挙動が design doc にしかない現状は解消しない。
