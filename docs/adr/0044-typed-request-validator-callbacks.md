# ADR 0044: API リクエスト検証を生成パッケージから直接呼び出す

- Status: Accepted
- Date: 2026-10-15

## Context

API コマンド生成器は、`request_validator` の値を文字列キーとして生成コードに埋め込み、全操作共通の `Runtime.ValidateRequest func(string, any) error` を呼び出していました。手書き関数側はキーを `switch` で振り分け、`any` を操作ごとのリクエスト型へ型アサーションしていたため、設定名、実装関数、リクエスト型の不一致をビルド時に検出できませんでした。検証関数をコマンド実装と別の IaaS リソースパッケージに置く構成も、検証関数だけを CLI の Runtime に再接続する必要があり、関連処理が分散していました。

IaaS と Ogen 系 API の生成コードと手書き実装を分離する既存構成は維持しながら、設定と実装の結び付きを Go の型検査で確認できる必要があります。

## Decision

- `request_validator` には、生成コマンドと同じ Go パッケージに定義する関数名を指定します。
- 生成器は入力リクエストを構築した後、SDK 呼び出し前に `request_validator(request)` を直接呼び出します。手書き検証関数も生成コマンドと同じ `*api` パッケージに置き、CLI の Runtime で接続しません。
- 検証が失敗した場合は従来どおりエラーを返し、API を呼び出しません。フラグ入力と JSON 入力のどちらも、同じリクエスト検証を通します。
- `handwritten: true` の操作も、手書きハンドラーから同じパッケージの検証関数を直接呼び出します。
- 検証器は無効な関数名、リクエスト型のない操作、生成型と同名の検証関数、同一関数名を異なるリクエスト型に使う設定を拒否します。
- 文字列キーによる検証処理のディスパッチ、検証目的の `any` 引数、Runtime callback と CLI の検証関数接続をなくします。既存の IaaS と EventBus の各 validator をコマンド実装と同じパッケージにまとめます。

## Consequences

設定した検証関数が存在しない、または引数型が異なる場合は、生成コードのビルド時に検出されます。validator ごとの文字列分岐や型アサーションがなくなり、CLI に Runtime 検証 callback を登録する処理も不要になります。

検証処理とコマンド処理は同じパッケージに配置します。生成器のテンプレート変更後は設定から全生成コードを再生成し、生成物の整合性とビルドを確認します。

## Alternatives considered

- 共通の `func(string, any) error` を維持して、命名規則だけを統一する案: リクエスト型の不一致が実行時まで検出されないため採用しません。
- 検証関数を別パッケージに置き、Runtime callback として接続する案: CLI の初期化に不要な接続コードを増やし、コマンドとその検証を分散させるため採用しません。
- リクエスト検証も `request_transform` に統合する案: 検証と入力変換の目的を混同し、JSON 入力に対する処理の意味を変えるため採用しません。
