# ADR 0082: 高レベルコマンドの待機オプション

- Status: Accepted
- Date: 2026-11-13

## 背景

[ADR 0075](0075-high-level-command-tier.md) で高レベルコマンド層 `skr <domain>` を導入し、低レベル `<domain>-api` は SDK の操作と 1 対 1 で対応させることにしました。高レベル層は作業単位を内製する場所です。

`skr apprun-dedicated` では、デプロイやロールバック、停止、削除で API 反映が非同期に完了するため、`--no-wait` と `--wait-timeout` を設けてデフォルトで待機しています ([ADR 0079](0079-apprun-dedicated-high-level-commands.md))。[#257](https://github.com/sacloud/skr/issues/257) では、AppRun Dedicated のオートスケーリンググループやクラスタの作成・削除でも同様の待ち合わせが必要である一方、チュートリアルで利用者が自前の待ちループを書くのは高レベルコマンドの思想と不整合であると指摘されています。

低レベル API コマンドに `--wait` 系のフラグを入れると、API に存在しない「待ち合わせ」という操作を持ち込むことになり、層の責務が曖昧になります。したがって、待ち合わせは高レベル層で吸収すべきです。

## 決定

- 待機が必要な高レベルコマンドは、デフォルトで待機します。
- `--no-wait` フラグで待機を省略します。
- `--wait-timeout DURATION` フラグで待機のタイムアウトを指定します。未指定時の既定値は操作ごとに定めます。たとえば `skr apprun-dedicated` では 5 分です。
- 待機は高レベルコマンドの責務とし、低レベル `<domain>-api` コマンドには `--wait` 系のフラグを設けません。
- 待機中はポーリング間隔とタイムアウトを明示します。タイムアウトした場合、変更操作自体は既に完了していることがあるため、エラーメッセージに状態確認の方法を示します。
- 待機が不要な高レベルコマンドは、`--no-wait` と `--wait-timeout` を設けません。

## 影響

- 既存の `skr apprun-dedicated` は本規約に既に沿っています。
- 今後待機が必要な高レベルコマンドを設計するときの指針となります。
- チュートリアルや利用者スクリプトから、エラー文言の文字列マッチを使った待ちループが減ります。
- 待機処理のテストは、fake やモックを使った時間制御で完了を検証し、ライブ E2E では実際の反映時間を待ちます。

## 検討した選択肢

- `--wait` / `--no-wait` の両方を設ける方式: bool フラグを 2 つ設けると排他制御が複雑になり、両方指定されたときの挙動を説明しにくくなります。デフォルトで待機し、`--no-wait` だけで省略できる方が簡潔なため採用しません。
- 低レベル `<domain>-api` にも `--wait` 系フラグを設ける方式: API に存在しない操作を持ち込むため、層の汚染になります。高レベル層で待ち合わせを吸収する方針を採用します。
- 汎用の `wait` サブコマンドを設ける方式 ([#257](https://github.com/sacloud/skr/issues/257) の案 B): 待ち処理だけを primitive 化できますが、高レベルコマンドの「作業単位を内製する」思想から外れ、ID 配管が残るため採用しません。
