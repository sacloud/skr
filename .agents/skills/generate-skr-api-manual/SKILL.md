# skr API チュートリアルの作成

実装済みの `skr <service>-api` コマンドについて、ユーザー向けチュートリアルを作成するときにこのスキルを使用してください。チュートリアルでは CLI の構文だけでなくサービスの利用手順も説明します。`--help` の内容をそのままコマンドリファレンスとしてコピーするものではありません。

生成するチュートリアルは `docs/manual/tutorials/` に配置します。IaaS API のように複数のリソースを扱う場合は `docs/manual/tutorials/<service>-api/<resource>.md` に分け、それ以外は `docs/manual/tutorials/<service>-api.md` とします。チュートリアル以外の利用者向け解説も `docs/manual/` に配置します。reStructuredText は生成しないでください。

## 原則と情報源の方針

- サービスの動作、ユースケース、リソースの意味と関係、前提条件、制約、例は、公式サービスマニュアル `https://manual.sakura.ad.jp/cloud/` と、このリポジトリが使用する正確なバージョンの `sacloud-sdk-go` のドキュメントだけを根拠にします。
- 過去の知識、検索結果の要約、第三者の記事、別サービスの例から製品の動作を推測しないでください。サービス固有の事実にはそれぞれ情報源を記録します。必要な事実に権威ある情報源がない場合は、記載を省くか、不足している情報を説明して作業を止めてください。
- 利用者向けの本文では、確認済みの仕様を CLI 自身の説明として直接記述します。「公式マニュアルによると」「マニュアルでは」のように、第三者の説明として距離を置く言い方は避けてください。根拠は該当箇所にリンクし、情報源の記録は執筆時の事実確認に使います。
- コマンドパス、フラグ、JSON リクエスト形式、出力の動作、ファイル／標準入力の構文については、現在の skr コマンド実装と実際に表示される `--help` を正とします。usacloud のコマンドをコピーしたり、usacloud との互換性を約束したりしないでください。
- SDK のリクエスト型に含まれる値を API の入力フィールドとして説明する前に、SDK が実際に API へ送信するリクエストまで追跡します。SDK が検索や変換に使う補助入力は API フィールドと混同せず、CLI が対応する場合もその用途を正確に説明します。
- ドキュメントで裏付けられる事実と、テストで確認された動作を明確に区別します。ライブ環境でのエンドツーエンド動作を確認していないシナリオを、成功したものとして示してはいけません。
- 認証情報やアカウント固有のデータをチュートリアルに含めないでください。ID、名前、イベントソース、ゾーンなど環境によって異なる値にはプレースホルダーを使います。実際のプロファイル名、API トークン、秘密情報、アカウント ID、本番環境の出力やログを含めないでください。

## 入力と成果物

E2E テストやチュートリアルで `--request` を使いたくなった場合は、JSON を前提に書き進めないでください。既存オプションで表現できるか、限定的な CLI 拡張で簡潔にできるかを検討します。必要な入力、現状の制約、拡張案と影響、JSON を残す理由を整理し、入力経路と拡張の可否をユーザーに確認してから実装・執筆してください。秘密情報や複雑な構成を無理にフラグ化せず、JSON 入力自体を検証するテストは維持します。

[ADR 0049](../../../docs/adr/0049-internet-workflow-options.md) の次の拡張は許容する実装範囲です。この範囲の再承認は不要であり、実装・維持したオプションを E2E とチュートリアルで利用します。未実装の構文を先行して例示せず、実際の `--help` と照合してください。

- Server Create の `--nic upstream=SWITCH_ID` は正の整数のスイッチ ID を指定します。既存の `shared` と `disconnected` も利用できます。ゲスト OS の IP アドレスは設定しません。
- Internet・Server・Disk の Find の `--name` は、単一条件の部分一致検索です。値を分割せず1要素の `Names` に変換し、複数名は JSON に残します。完全一致とは説明しません。
- Internet Delete の `--force` と `--fail-if-not-found` は、API 本文のフィールドではなく削除の動作オプションです。`--force` は IPv6 の無効化と `NextHop` のある追加サブネットの削除を伴うため、削除範囲を説明します。

他の配列や操作へ自動的に一般化せず、JSON 入力と個別オプションとの相互排他を維持します。

執筆前に、次の内容を確認してください。

- 対象コマンドが存在し、その `--help` に現在の構文が記載されていること
- リポジトリの SDK バージョンと、対象サービスの SDK ドキュメント。SDK の入力値が補助入力か API に送信されるフィールドかも確認すること
- サービスのモデルや手順を裏付ける公式マニュアルのページ
- 有用なエンドツーエンドのシナリオに必要なリソース、依存関係、認証情報、権限、観察方法
- ライブテストで作成、変更、削除する正確なリソースと、安全なクリーンアップ方法

チュートリアルは前述の配置規則に従って作成します。`assets/tutorial.md.tmpl` は構成の参考にし、プレースホルダーを残したままにしないでください。一時的な根拠整理の表はリポジトリ外に置き、調査メモをコミットしないでください。根拠整理表では各事実の横に情報源 URL を記録し、公式マニュアルまたはバージョン固定された SDK ドキュメントで追跡できる主張だけを残してください。

## 執筆手順

1. `AGENTS.md`、`go.mod`、コマンド実装、関連テスト、対象 SDK サービスのドキュメントを読みます。
2. `manual.sakura.ad.jp` のサービスマニュアルを読みます。サービスが解決する課題、概念とリソースの関係、必要な前提条件、制約、チュートリアルで示す結果を確認します。
3. ルート、リソース、操作の各ヘルプを表示して確認します。チュートリアルの JSON 例が、実装済みのリクエストデコーダーと SDK モデルに合っていることを確かめます。ヘルプやコードとドキュメントに食い違いがあれば、どちらかを黙って選ばず、公開前に解決してください。
   少数の値で済む操作は、実装済みのフラグで書けるか確認します。複雑な入力は JSON ファイルを使い、未実装のフラグや `--request` との併用を例示しないでください。
4. 単に `create`、`read`、`list` が成功するだけではなく、サービスの有用な動作を示す、小さく再現可能なシナリオを設計します。必要な宛先や依存サービスも含め、実際の結果をどう観察できるかを明らかにします。
   実装前にシナリオとリソースの範囲をユーザーに提示し、承認を得ます。公式 FAQ も確認し、全宛先停止時やフォールバック先未設定時の仕様を踏まえた構成にします。空出力やコマンド成功だけで判断せず、正常応答と期待する内容を成功条件にします。仕様と証跡が矛盾する結果を、正常動作としてチュートリアルへ転記しないでください。
5. セットアップ、認証、既存リソースと、チュートリアルが新たに作成するリソースを区別します。リソースを変更するコマンドの前に、ユーザーが指定する値と必要な権限をすべて説明します。
6. `references/markdown-writing-guideline.md` とテンプレートに沿って Markdown を作成します。リソースの作成順序を説明し、コピー可能なコマンドまたは JSON ファイル、観察可能な結果の確認方法、依存関係を逆順にたどるクリーンアップ手順を記載します。
7. `list`、`find` などの一覧・検索結果を使って作成や削除を検証する場合は、`--query` で確認に必要な項目を投影した JSON を使い、出力例も直後に掲載します。例えば `map({ID,Name})` で配列を保ち、空一覧は `[]` として示します。項目名は対象 API の出力形状に合わせ、識別に必要な説明や状態も残します。ID、名前、説明、時刻など環境固有の値はマスクまたは置換し、編集したことを明記します。全件一覧のうち一部だけを示す場合は、その旨も記載します。
8. すべてのコマンドを実際の CLI `--help` と照合し、サービスに関する記述を根拠整理表と照合します。一般化できない値はプレースホルダーと明記し、イベント種別、列挙値、ソース識別子、成功した出力例を作り上げないでください。
9. Markdown リンクチェッカーとそのテストを実行します。ドキュメントをプレビューし、ローカルリンク、見出し、コードフェンス、コマンド表示を確認します。
10. 生成したチュートリアルのパスと、エンドツーエンドの動作を sakumock、ライブサービス、ドキュメントのみのいずれで確認したかを報告します。残る手動確認や依存事項があれば明示します。

## ライブ E2E の再実行と証跡

公開するすべての末端サブコマンドにはライブ E2E テストを必須とします。チュートリアルの全手順を対応させ、掲載していない操作も少なくとも1回正常実行して応答内容を照合します。1サービスに複数のシナリオを設けても構いません。条件付きの手順や追加リソースが必要な操作は独立したシナリオにできます。シナリオテストの実装状況と実際のライブ成功を区別し、API エラーや依存不足も設計文書と `PLAN.md` に残します。延期には利用者の合意と追跡 Issue が必要です。fake の成功、失敗応答、ヘルプ表示だけでは検証済みとしません。

配置と命名は [`AGENTS.md` の E2E 規則](../../../AGENTS.md#e2e-の配置と命名)に従います。E2E シナリオは testing.T ベースの `scenario_<snake_case>_test.go` にし、共有の helper (`test/e2e/internal/helper`) でビルド済みの skr を実行します。`SKR_E2E` が未設定、または `skr-e2e` プロファイルが存在しないならテストをスキップし、通常の `go test` では実環境を変更しません。実行記録は Git 対象外の `e2e-output/` 配下に保存され、識別名は `helper.New` で指定し、`config` は `c0nfig` に置き換えます。

ライブ検証の承認を得た場合は、手作業の成功だけで終わらせず、同じ管理操作を再実行できる E2E シナリオテストにします。このリポジトリでは `test/e2e/<resource>/` に testing.T ベースのテストを置き、共有の helper でビルド済みの skr を呼び出して実際の CLI パスを検証します。対象のサービスに応じて作成、検索、参照、更新、削除を組み合わせ、返された ID と名前などを照合してください。通信など Sandbox で観察できない動作は検証済みとしません。

- 実行前に対象プロファイル、プロジェクト、ゾーンと権限を確認します。対象範囲と副作用を明示し、破壊的な事前処理を含む実行について承認を得ます。テストは `SKR_E2E` が未設定のときにスキップするため、通常の `go test` では意図しない起動が起こりません。
- テスト専用と分かる固定の名前や接頭辞を使用できます。再実行時に残存リソースを削除する場合は、対象と事前削除を明示して承認を得たときに限ります。対象範囲の検索結果を最後まで取得し、名前だけでなく専用の説明値など複数の識別情報と ID を確認します。削除直前にも読み直して照合し、曖昧な一致や検索失敗時は変更せず停止します。
- 作成結果を保存し、成功時と途中失敗時の両方で今回作成したリソースの削除を試みます。ID や識別情報を再確認してから削除し、削除後に残存しないことを検査します。安全に特定できなければ推測で削除せず、エラーと手動確認の必要性を通知します。
- 後片付け時の無効化・切断・設定復元も変更操作として扱います。操作直前に現在値を読み直し、リソース ID と所属だけでなく、暗号化キー ID、レプリケーション先など今回設定した値も照合します。`defer` やキャンセル後の片付けでも省略しません。不在なら変更せず終了し、不一致・不正応答・必須 ID の欠落・照会失敗なら変更 API を呼ばず、手動確認が必要なエラーを返します。
- 後片付けでは、設定の別 ID・別キーへの置換、不正応答、照会失敗、既に不在、キャンセル直後の設定変更でも変更 API を呼ばない照合を実装し、後片付けの失敗がテストの結果に反映されることを確認します。チュートリアルの手動手順にも同じ再照合を記載します。
- チュートリアルでも依存リソースの ID を作成直後に控え、削除直前に同じ ID・指定内容・接続状態を確認する手順にします。名前検索で表示されたものだけを確認し、別名の接続リソースも含む一括削除を実行する手順にはしません。シナリオテストで確認した安全条件を手動手順にも反映し、同名・同仕様だけで削除対象を特定しないでください。
- 非同期の反映待ちは、確認すべき正常状態と再試行の間隔・期限、失敗時の確認事項を示します。ネストした設定が全体置換される場合は、親設定の省略とは区別し、保持したい内部項目の再指定を説明します。cloud-init の手順では対応タグとサイズを確認し、通常の OS アーカイブとの取り違えを防ぎます。
- 各操作の入力、出力、エラーを証跡として Git 管理外の場所に保存します。認証情報をコマンド引数に含めず、記録対象に秘密情報がないか確認し、保存先とファイルの権限を制限します。証跡にアカウント固有の情報が含まれ得るため、リポジトリに追加・共有しません。失敗時も保存先を示します。
- E2E シナリオの照合、事前削除、失敗時の片付けはシナリオテスト自体に実装します。ライブ実行の手順と証跡の扱いは開発者向け文書に記録し、利用者向けチュートリアルには開発用スクリプトの実行手順や「検証状況」の節を追加しません。

## ライブサービスの安全性

ライブのチュートリアルテストでは、課金対象や本番リソースの作成、既存リソースの変更、通知・メッセージの送信、自動化の起動、データの削除を伴う可能性があります。チュートリアル作成の依頼だけを根拠に、これらを実施してはいけません。

ライブ環境を変更する前に、次のすべてを実施してください。

1. 対象のプロファイル／ゾーンまたはプロジェクト、依存関係、対象リソースと具体的な操作、副作用、クリーンアップ計画をユーザーに提示します。
2. そのライブテストに対する明示的な承認を得ます。
3. 有効なプロファイル／設定を確認し、承認されたアカウントと範囲だけを使用します。
4. 既存のリソースを再利用したり削除したりしないでください。例外は、前述の条件で明示的に承認されたテスト専用リソースの事前削除だけです。
5. 秘密情報はローカルの保護されたファイル、またはサポートされている安全な入力方法で扱います。ユーザーに会話で認証情報を貼り付けるよう求めたり、シェル履歴に残したりしないでください。
6. サービスの動作を確認してから、テスト用に作成したリソースだけをクリーンアップし、削除されたことを確認します。

承認、必要な依存関係、安全なクリーンアップ、実際の動作を観察する方法のいずれかがない場合、ライブ環境でエンドツーエンドの動作を検証したと主張してはいけません。対応する場合は sakumock でリクエスト／レスポンスを確認し、その制約を明記します。チュートリアルの中心的な主張をライブテストなしでは説明・裏付けできない場合、CRUD だけのテストで代替せず、作業を止めて阻害要因を報告してください。

## 必須セクション

該当する内容を、すべてのチュートリアルで扱ってください。

1. **目的** — 公式情報源を根拠に、サービスをいつ、なぜ使うかを説明します。
2. **前提条件** — skr のバージョン／コマンド、認証設定、権限、既存リソース、依存サービスを記載します。
3. **手順とリソース** — 作成するリソースとその順序を説明します。
4. **コマンドヘルプの確認** — 手順に関係するルート／リソース／操作のヘルプを示します。
5. **作成／設定** — 有効な JSON ファイルやコマンドを示し、必須フィールド、単位、選択肢、プレースホルダーを説明します。
6. **動作の確認** — CRUD を超える観察可能なサービス結果を示すか、ライブで未検証の部分とその理由を明記します。
7. **クリーンアップ** — チュートリアルで作成したリソースだけを依存関係の逆順で削除し、削除を確認します。
8. **参考情報** — 関連するさくらのクラウドマニュアルと SDK ドキュメントへのリンクを記載します。CLI のヘルプは構文確認に使い、参考資料には含めません。

チュートリアルに関係のないセクションや事実を無理に含めないでください。API フィールドの長い一覧より、簡潔で完結したシナリオを優先します。

## 検証

チェッカーのテストを実行します。

```sh
python3 -m unittest discover -s .agents/skills/generate-skr-api-manual/scripts -p 'test_*.py'
```

生成したチュートリアルのリンクを確認します。

```sh
python3 ./.agents/skills/generate-skr-api-manual/scripts/check_tutorial_links.py
```

チェッカーには Markdown ファイルを明示的に渡すこともできます。また、`--timeout`、`--retries`、`--jobs` を指定できます。外部リンクの確認に失敗した場合は、公式情報源を再確認し、移動していればリンクを更新してください。チェックを通すためだけに正しい引用を削除してはいけません。
