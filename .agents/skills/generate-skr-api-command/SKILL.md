# skr SDK API コマンドの作成

`github.com/sacloud/sacloud-sdk-go` を使う `skr <service>-api` コマンドを追加するときに、このスキルを使用してください。skr の現在のアーキテクチャと Go バージョンに合わせて実装します。旧 `usacloud` CLI との互換性を前提にしたり、内部パッケージを流用したりしないでください。

## 基本方針

- CLI のヘルプを主要なユーザーガイドとして扱います。ユーザーがソースコードを読む前に `--help` を確認するだけで、サービスの使い方、入力の準備、コマンドの実行、出力の解釈ができるようにします。
- サービスの動作、フィールドの意味、前提条件、単位、例は、対象 SDK のドキュメントと `manual.sakura.ad.jp` の情報だけを根拠にします。不明点を推測、過去の知識、無関係なサービスの例で補わないでください。
- ヘルプでは、根拠を確認できたサービス仕様を CLI 自身の説明として直接記述し、「公式マニュアルによると」など第三者の説明として距離を置く表現は使わないでください。必要な根拠リンクは示し、情報源の調査記録は実装時の確認に使ってください。
- 公開 SDK のインターフェースとモデルをラップします。生の HTTP 通信で SDK の動作を再実装したり、SDK 内部の実装コードをコピーしたりしないでください。
- SDK のリクエスト型にある値を CLI の API 入力として扱う前に、公開 API に実際に送信されるフィールドかを確認してください。SDK が補助入力を検索や変換に使い、API 用リクエストから別の値を作る場合、その補助入力は API フィールドとしてフラグ化しません。別のユーザー向け操作として公開する場合は、API 入力と混同しない用途・ヘルプ・根拠を明確にしてください。
- 変更範囲を絞り、既存の動作を維持し、新しいユーザー向けコマンドをすべてドキュメント化します。コマンド追加は、実装・テストだけで終わらせず、再実行可能なライブ E2E と利用者向けチュートリアルまでを一連の作業として扱います。
- 低レベル IaaS API コマンドを `cmd/apigen-iaas` で生成する場合は、設定 JSON・生成コード・検証手順について [`apigen-iaas` スキル](../apigen-iaas/SKILL.md)も適用します。生成コードを直接編集しないでください。

## 作業手順

### 1. 対応する API とサービスの利用手順を確認する

`AGENTS.md`、`go.mod`、`internal/cli/` の CLI 実装、対象 SDK パッケージ、関連するテストとドキュメントを確認します。このリポジトリが使用する SDK のバージョンを特定し、次の項目を確認してください。

- 公開サービス操作インターフェースとそのメソッド
- リソース型、リクエスト／レスポンスモデル、union／discriminator フィールド、省略値や null の意味
- 各操作の必須入力、フィールドの型、ゼロ値と未指定の違い、フィールド間の依存関係
- SDK のリクエスト値が実際の API リクエストへどう変換されるか。SDK 固有の補助入力、API に送信されないフィールド、別 API 呼び出しを誘発する値を通常の API フィールドと区別する
- 必要なセットアップの順序と、リソース間の参照方法
- 認証、エンドポイント設定、単位、対応値、ユーザーに伝えるべきサービス上の制限

サービスの動作の根拠には SDK と公式マニュアルを使用してください。重要なフィールド、discriminator、リソース間の関係、前提条件がこれらの情報源で明らかでない場合、答えを作り上げず、機能範囲を狭めるか、確認が必要な点を報告して作業を止めてください。既存実装が提示されている場合は参考にしつつ、その動作を skr 向けに適応し、旧フレームワークや依存関係を持ち込まないでください。

### 2. コマンドツリーとヘルプを設計する

ハンドラーを実装する前に、コマンドパス、リソース名、操作名、リクエスト形式、出力を設計します。`internal/cli/` とドメインパッケージの既存 Kong パターンに従ってください。

- Go のフィールド名から望む表記にならない場合は、明示的な `name` を付けてルート CLI に登録します。
- Kong のコマンド構造体と `Run(*kong.Context) error` ハンドラーで、リソースと操作の階層を表現します。
- 共通の説明ではリソース固有のフィールド、制約、例が伝わらなくなる場合は、リソースごとのコマンド型を使用します。
- SDK クライアントの生成は小さなヘルパーにまとめ、`os.Environ()` から `saclient.Client` を初期化します。SDK のサービスクライアントと操作コンストラクターを使用してください。
- SDK、入力、ファイル、出力に関するエラーは Kong に返します。エラーを無視したり、成功したように見えるデフォルト値に置き換えたりしないでください。

#### IaaS のゾーン指定

IaaS API コマンドの検索では、フラグまたは `--request` JSON で単一の対象ゾーンを指定します。`--zone all` と JSON の `Zone: "all"` はサポートせず、API 呼び出し前に拒否します。ゾーンをまたぐ検索の反復や結果集約は追加せず、コマンドヘルプとチュートリアルでは対象ゾーンの指定方法を説明してください。

サービス、リソース、操作、フラグという実際に表示される各コマンド階層のヘルプを作成します。該当する場合は、次の内容を説明してください。

- 各リソースが表すものと、他のリソースとの関係
- 先に作成するリソースと、後続コマンドで使う ID
- 必須／任意フィールド、有効な値、単位、相互排他となる選択肢
- 更新が部分更新かどうか、省略フィールドの扱い、nullable フィールドのクリア方法
- 認証／設定の要件と出力形式
- 秘密情報をコマンドライン引数に含めず、ファイル／標準入力から渡す方法
- ユーザーが置き換える値を明示した、コピー可能なコマンド例

例は SDK／マニュアルで確認できる内容に限定してください。イベントソース、ID、認証情報などユーザー環境で異なる値は、プレースホルダーと明記します。コマンド例には秘密情報を書かないでください。

### リクエスト入力経路を決める

E2E テストやチュートリアルで `--request` を使いたくなった場合は、JSON を前提に書き進めないでください。複雑な設定や配列を含む操作も JSON 専用と決めつけず、サービスの主要な作業で必要な入力を、ネストしたスカラー用の専用フラグや厳密な構造化形式の反復可能オプションで簡潔に表現できるか検討します。必要な入力、現状の制約、拡張案と影響、JSON を残す理由を整理し、独自構文の追加をユーザーに確認してから実装・執筆してください。追加する場合は SDK が API に送る値と公式仕様に対応させ、JSON 経路を維持し、両経路を相互排他にします。省略と明示値、未知・重複キー、構文エラー、変換結果をテストし、構文をヘルプ・チュートリアル・ADR・設計文書に記録します。秘密情報や複雑な構成を無理にフラグ化せず、JSON 入力自体を検証するテストは維持します。

[ADR 0049](../../../docs/adr/0049-internet-workflow-options.md) の次の拡張は許容する実装範囲です。この範囲の再承認は不要であり、実装・維持したオプションを E2E とチュートリアルで利用します。他の配列や操作へ自動的に一般化しません。

- Server Create の `--nic upstream=SWITCH_ID` は正の整数のスイッチ ID を受け付けます。既存の `shared` と `disconnected` も維持します。
- Internet・Server・Disk の Find の `--name` は、単一条件の部分一致検索です。値を分割せず1要素の `Names` に変換し、複数名は JSON に残します。
- Internet Delete の `--force` と `--fail-if-not-found` は、API 本文のフィールドではなく削除の動作オプションです。`--force` は IPv6 の無効化と `NextHop` のある追加サブネットの削除を伴います。

この範囲でも JSON 入力と個別オプションとの相互排他を維持します。

[API リクエスト入力の方針](../../../docs/adr/0007-api-request-input.md)を、SDK リクエストを受け取る操作に次の順序で適用してください。位置引数だけを使う既存の操作を `--request` に強制変更しないでください。SDK のフィールド数で入力経路を決めないでください。

1. SDK のメソッド引数、リクエスト型、`Validate` と実装から、有効な最小リクエストに必要な値を確認します。条件付きの必須値や、実際の利用に必要な値も含めます。SDK リクエストの各値が実際の API リクエストに含まれるか、SDK の補助入力として検索・変換・追加 API 呼び出しに使われるかも追跡します。API に送信されない補助入力を API フィールドとしてフラグ化しません。`required_with` などの検証タグを無条件の必須値として数えず、SDK と公式資料で条件と省略時の意味を確認します。不明なら推測してフラグ化せず、根拠を調べてから決めます。
2. 入力不要の操作には入力用フラグや `--request` を追加しません。SDK リクエストを JSON で受け付ける操作は、全体を渡す `--request` 経路を維持します。対応済みの直接 JSON と `@path.json` を壊さないでください。秘密情報はインライン JSON やフラグを使わず、安全なファイルまたは対応する標準入力で渡します。

   Ogen 系生成コマンドで秘密情報を含む可能性がある操作には `request_file_only: true` を指定します。`request_type` が必須です。生成された操作は `--request` を必須とし、`@path.json` または `-`（標準入力）だけを受け付けることをテストします。
3. 必要な値がすべて独立した単一スカラー値で、フラグだけで有効な最小リクエストを構築できる場合にフラグ経路を追加します。SDK リクエスト上で値が単一の設定オブジェクトにネストしている場合でも、それが少数の独立したスカラー値だけで構成される一般的な設定操作なら、対応するフラットな CLI フラグを追加できます。たとえば `Settings` にタイムアウトと保存期間の2値だけを指定する操作では、両値を個別フラグで受け付け、同じ SDK リクエスト型のネスト構造に組み立てます。IaaS API ではトップレベルの任意 `Tags` 配列を `--tags` のカンマ区切り値として受け付けられますが、これは最小リクエストに必要な配列をフラグ化する根拠にはなりません。必要な値が配列、map、union、`null`、秘密情報、複数の複雑なオブジェクトを含む場合や、条件付き入力をフラグで一意に表現できない場合は JSON 経路だけにします。SDK の `Validate` が通るだけで実用的なリクエストになるとは仮定しないでください。
4. フラグ経路では、最小リクエストに必要な値をすべてフラグ化します。任意値は、トップレベルまたは前項の単純な設定オブジェクト内にある独立した単一スカラーで、未指定と明示指定の違いを SDK リクエストで保持できるものをフラグ化します。例外として IaaS API のトップレベル `Tags` 配列は、個別フラグ入力に対応する操作で `--tags` に指定できます。生成設定では `type: "[]string"`、`separator: ","` を指定し、必要に応じて `conversion: "types.Tags"` を使います。更新の未指定と明示指定を区別するため、更新リクエストで `Tags` がポインター型なら `pointer: true` にします。その他の複雑な値、配列、nullable な値、秘密情報は JSON 経路に残します。フラグは SDK フィールドに対応する小文字の kebab-case とし、略語は `ID` → `id` のように小文字化します。ネスト値をフラット化する場合も、どの SDK フィールドに対応するかヘルプで示します。この例外の範囲は [ADR 0035](../../../docs/adr/0035-iaas-tags-flag.md) に従います。
5. `--request` と個別フラグは相互排他にします。`--request` が指定されたら JSON だけをデコードし、フラグが指定されたらフラグだけから同じ SDK リクエスト型を構築します。両方の明示指定は値が `false`、`0`、空文字列でもエラーにし、マージしません。どちらも指定されておらず入力が必要なら、SDK を呼び出す前に必須入力の欠落をエラーにします。フラグ経路で必須値が欠けた場合もエラーにします。JSON 経路を選ぶときは個別フラグを必須として扱わないでください。
6. 任意フラグの明示指定を検出できる方法を使い、未指定の値を勝手に SDK リクエストへ設定しません。特に部分更新では未指定を「変更なし」として保持し、明示的なゼロ値だけを設定します。`null` や値のクリアは SDK の意味を確認し、JSON 経路で表現します。どちらの経路でも同じ公開 SDK 操作を呼び出してください。

ネストした設定では、親設定を省略した場合と、指定した設定内で項目を省略した場合を区別してください。設定全体を置き換える操作を「省略項目は変更しません」とだけ説明しないでください。保持したい内部項目の再指定が必要ならヘルプに明記し、既存の非ゼロ値を持つ設定に対して、一部指定と全項目の再指定を公開 SDK のリクエスト変換まで通してテストします。

各操作の `--help` には、フラグ経路の利用可否、必要・任意フラグ、`--request` との排他性、JSON でのみ扱う項目、実際に動く最小の実行例を記載します。`--tags` を設ける場合はカンマ区切りであることと SDK リクエストの `Tags` フィールドに対応することを説明し、JSON 経路での `Tags` 配列も引き続き使えることを示します。ネスト値をフラット化したフラグは、SDK リクエスト内の対応先も示します。JSON 専用の操作にはフラグの例を載せません。既存コマンドを変更するときは、フラグ実装後に README とチュートリアルの単純な例を更新し、複雑な入力例は JSON ファイルのままにしてください。

### 3. SDK のリクエストとレスポンスを実装する

- 公開 SDK のリクエスト／レスポンス型を使用します。必須のプロバイダークラス、sum type の選択、その他の操作上の不変条件を維持してください。コマンドがリソース型を特定しており、SDK が要求する場合は、そのサービス固有の discriminator をコマンド層で設定します。
- リクエスト入力の構文をフラグのヘルプで明示します。JSON を受け付ける場合は、SDK のリクエスト形式、インラインまたは `@path.json` で渡せるか、コマンド側で設定するフィールドを説明します。シェルのクォートで曖昧になりやすい複雑な例は、ドキュメント内のファイルに記載してください。
- SDK モデル、特に optional 値や sum type を含むモデルでは、SDK の JSON デコード／エンコード動作を使用します。通常の Go フィールドの JSON 動作と同じだと決めつけないでください。
- 出力形式をドキュメント化してテストします。有用なスカラー ID やリソースデータを出力に残し、SDK がエラーを返したときに成功したような結果を返さないでください。
- 公開サービス API でサポートされ、依頼内容から正当化できる操作だけを公開します。

### 4. sakumock でテストを追加する

API 動作のテストには、対応している場合 `github.com/sacloud/sakumock/<service>` を使用してください。対象の IaaS 操作に未対応の場合は [ADR 0006](../../../docs/adr/0006-iaas-api-resource-implementation.md) に従い、SDK の公開 caller interface を満たすテスト用モックを使用します。

- sakumock を使う場合は、サービスのテストサーバーを起動し、テストのクリーンアップで終了します。
- ダミーの認証情報と SDK のエンドポイント環境変数を設定します。プロファイルの検出がテストに影響する可能性がある場合は、分離したプロファイルディレクトリを使用します。
- 実際の CLI コマンドパスを sakumock または対象の IaaS テスト用モックに対して実行します。実装した操作のフローで、送信リクエストの設定と返却結果を検証します。
- 利用可能であれば、sakumock の検査 API で秘密情報を設定する操作を検証します。
- リクエストのデコード、ファイル／標準入力の扱い、バリデーション、エラー経路には対象を絞ったユニットテストを追加します。ヘルプテストでは、コマンド名が存在することだけでなく、表示されたヘルプに手順、入力形式、例の重要な情報が含まれていることを確認します。
- 両経路がある操作では、フラグと JSON が同じ SDK リクエストになることを確認します。フラグ経路の必須値不足、JSON だけの指定、両経路の併用、未指定と明示的な `false`・`0`・空文字列、部分更新で省略した値、JSON 専用の複雑な値を検証します。JSON だけの操作は JSON 入力を検証し、入力不要の操作には不要な入力フラグがないことを確認します。
- IaaS の `--tags` を追加・変更する場合は、区切り文字から文字列配列への変換、SDK `Tags` フィールドへの設定、JSON 配列入力との同値性、`--request` との併用拒否、更新で未指定のタグが維持されることをテストします。ライブ E2E が対象リソースを作成・更新する場合はタグを設定・照合し、クリーンアップ対象の識別確認も維持します。

偽の API 実装はコマンドの純粋なロジックを分離するのに役立つ場合がありますが、SDK のリクエスト／レスポンス経路を利用可能な sakumock または IaaS テスト用モックで確認する代わりにはなりません。

### 5. コマンド全体をドキュメント化して検証する

- 公開するすべての末端サブコマンドにはライブ E2E テストを必須とし、少なくとも1回正常実行して応答内容を照合します。チュートリアルへの掲載有無で範囲を絞りません。1サービスに複数のシナリオを設けても構いません。コマンドツリーとシナリオの対応をテストし、コマンド追加時の網羅漏れを検出します。シナリオ実装済みとライブ成功済みを区別し、API エラーや依存不足も記録します。延期には利用者の合意と追跡 Issue が必要です。fake の成功、失敗応答、ヘルプ表示だけでは検証済みとしません。
- 配置と命名は [`AGENTS.md` の E2E 規則](../../../AGENTS.md#e2e-の配置と命名)に従います。E2E シナリオは testing.T ベースの `scenario_<snake_case>_test.go` にし、共有の helper (`test/e2e/internal/helper`) でビルド済みの skr を実行します。`SKR_E2E` が未設定ならテストをスキップし、通常の `go test` では実環境を変更しません。実行記録は Git 対象外の `e2e-output/` 配下に保存され、識別名は `helper.New` で指定し、`config` は `c0nfig` に置き換えます。
- ライブ E2E の実装前に、シナリオ・成功条件・必要な依存リソース・副作用・後片付けをユーザーに提示して承認を得ます。基本手順に加えて公式 FAQ の障害時・全停止時の仕様も確認し、切り替え前後を区別できる構成にします。fake も同じ仕様を再現し、実装に都合のよい期待値を作りません。
- 成功条件は応答ステータスと期待する内容で定義します。たとえば DNS は `NOERROR` と期待する IP の組み合わせを照合し、空出力や終了コード 0 だけで正常な除外と判断しません。作成・変更直後の反映待ちは期限を設け、途中のエラーも記録し、期限切れでは最後の応答とエラーを返します。仕様と矛盾する観察結果は調査し、根拠不足の成功判定は撤回して `PLAN.md` と関連文書も修正します。
- API コマンドには `test/e2e/<service-or-resource>/` に再実行可能なライブ E2E シナリオテストを追加します。IaaS のリソース操作では、対象サービスが利用できる場合は `is1b` を基本の実行先にします。ゾーンやサービスの制約で利用できない場合は、仕様と認証済み環境で確認した適切な対象を選び、その理由を記録します。
- ライブ E2E は `SKR_E2E` 環境変数を必須にし（未設定ならスキップ）、ランダムまたは衝突しない名前を使います。既存リソースを更新・削除せず、作成したリソースだけを識別情報と内容で確認してクリーンアップし、削除後の不在まで検証します。失敗時の後片付けはテスト関数の `defer` で行い、実行記録は helper が Git 対象外の `e2e-output/` に保存します。単発の shell 手順だけをライブ E2E の代わりにしません。
- ディスクなど暗黙に作成される依存リソースも、作成直後に今回の親リソースへの所属と指定内容を照合し、ID を保持します。削除時は保持した ID・識別情報・接続状態を確認し、同名・同仕様の別 ID を削除しません。ID 未確定時は手動確認を要求し、未確認の接続リソースを巻き込む一括削除は避けます。cloud-init を使う場合は、作成前に選択アーカイブの対応タグとディスクサイズを確認し、一般の OS 名検索だけで対応を判断しません。
- 後片付けも変更操作です。削除だけでなく、暗号化・レプリケーション・権限などの無効化、切断、設定復元の直前にも現在値を読み直し、保持したリソース ID・所属・設定内容と照合します。暗号化では現在の `kms_key_id` が今回指定したキー ID と一致する場合だけ無効化します。レプリケーションでは送信元・宛先の ID または名前とサイトを再照合します。作成時の一致、バケット名だけ、ローカルの成功フラグだけを根拠に変更しません。
- `defer` による後片付けでも、同じ照合を必須にします。明確な不在は変更せず終了します。不一致、不正 JSON、必須 ID の欠落、照会失敗では変更 API を呼ばず、後片付けエラーと手動確認の必要性を返します。所有不明の設定を、無効化や親リソース削除で強制的に片付けません。
- 後片付けでは、設定が別 ID・別キーへ変わる場合、反映待ち中の不一致、応答不正、照会失敗、既に不在でも変更 API を呼ばない照合を実装します。後片付けの失敗はテストの結果へ反映されます。安全な照合ができた場合だけ後片付けできるようにします。
- テストの結果はクラウドとローカル一時ファイルの後片付けより後に確定します。途中失敗でも後片付けを試み、削除拒否や後片付けの失敗がテストの失敗として確認できるようにします。
- 表示・証跡用の一覧確認は `--query` で必要な項目を投影した JSON を使い、デコードして形状と値を照合します。`map({ID,Name})` など配列を返す式を基本とし、空一覧は `[]` として確認します。安全性検証と後始末に必要な識別情報や状態は残し、すべての API 応答を一律に投影しません。
- ライブ E2E シナリオは、対象プロジェクトへの認証と、作成・更新・削除による影響を明示して実行します。ユーザーが実行を依頼していないときは、費用やリソース変更を伴う実環境テストを `SKR_E2E` なしで実行しません。認証済み環境が使えない場合もシナリオテストは実装し、ライブ実行が未実施であることを報告します。
- 実装したコマンドの操作フローを含む利用者向けチュートリアルを `docs/manual/tutorials/` に追加し、`docs/manual/README.md` からリンクします。認証、前提条件、実行順、ID の受け渡し、リクエストファイル、出力、注意事項、クリーンアップを説明します。検証を実施した日付、特定の1回の実行結果、削除済みという一時的な状態はマニュアルに書かず、読者が再現できる手順と恒常的な仕様を記載します。IaaS では [`generate-skr-api-manual`](../generate-skr-api-manual/SKILL.md) の手順も適用します。
- README の使用方法に、認証／設定要件、セットアップ順序、代表的なコマンド、リクエストファイルの使い方、出力の動作、関連する注意点を追加します。
- テスト用のシナリオとライブ E2E の両方で、作成、検索、参照、更新、削除など公開する操作を確認します。変更した Go ファイルに `gofmt` を実行し、対象テストを実行します。ルートコマンド登録や共通 CLI の動作を変更した場合は `go test ./...` も実行します。
- 利用可能であれば `make lint-go` と関連するドキュメントチェックを実行します。
- `make build` を実行し、ビルドしたコマンドのヘルプを簡単に確認します。
- このリポジトリの `Makefile` は `GO_ENTRY_FILE` と `GO_INSTALL_PACKAGE` を `./cmd/skr` に設定します。CLI のビルドとインストールではパッケージ全体が対象になります。
- `git diff --check` を確認し、無関係なファイルや生成物が追加されていないことを確かめます。
- API コマンドの実装作業は、ライブ E2E シナリオテスト、利用者向けチュートリアル、README の導線まで揃えて完了とします。チュートリアル作成では[skr API チュートリアル生成スキル](../generate-skr-api-manual/SKILL.md)を使用してください。
